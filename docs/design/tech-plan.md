- 状态：初稿，供后续各开发阶段讨论

- 文档定位：说明需求边界、技术选型、大致架构、数据模型方向、Quick Capture 与 AI 总结的设计思路、阶段规划、风险与待定项。

## 1. 项目定位

自用的跨平台主动式个人记录工具，同时支持 Windows 与 macOS。

核心使用方式：程序长期后台常驻，用户在任何场景下通过全局快捷键调起一个轻量快速记录窗口，主动写下当前的想法、任务、决定、问题或灵感；内容按日期自动归集，并支持每日 AI 总结与结构化信息提取。

项目已明确放弃"后台被动采集用户在各软件中的输入内容"的方案（噪声大、采集质量不稳定），本文所有设计均以"主动记录"为前提，不引入任何被动监听能力。

## 2. 需求边界

### 2.1 已确认需求

| 分类 | 需求 |
|---|---|
| 平台 | 同时支持 Windows 与 macOS；维护一套统一项目与一套主要业务代码；平台差异（托盘/菜单栏、窗口行为、快捷键、便携目录与路径解析）须集中封装，不扩散到业务逻辑 |
| 分发 | 便携版（免安装、不需管理员权限）；不产出 MSI/NSIS 安装包；macOS 为未签名 `.app`，不做公证；不要求对外分发 |
| 常驻 | 由用户手动启动后长期后台常驻（不做开机自启，见 §2.5 #10）；主窗口关闭后继续运行；系统休眠后恢复；异常退出后重启能恢复必要状态；低 CPU、低内存、低频磁盘写入；不得设计成高频轮询架构 |
| 快速记录 | 全局快捷键调起；窗口快速显示；自动聚焦输入框；纯文本多行输入；支持中文输入法；快捷键保存；Esc 快速隐藏；未提交内容自动保存为草稿；再次调起恢复草稿；保存后清空输入并隐藏；尽量减少对用户原工作流程的干扰；快捷键需支持自定义并考虑冲突检测 |
| 入口 | Windows 托盘入口；macOS 菜单栏入口；可快速暂停或退出 |
| 记录内容 | 每次主动输入为一条独立 Entry；首版不做前置分类；分类、标签与 AI 提取属后续处理 |
| 组织方式 | 以日期为主要浏览维度；支持今日、历史日期、按日期查看全部 Entry；记录创建时间与修改时间；跨午夜后日期归属正确（以实际创建时间为主）；不做「文件夹→笔记本→页面→子页面」层级 |
| 草稿 | 输入过程中自动保存；防抖写入；能应对异常退出、系统突然关闭、误按 Esc；再次调起可恢复；自动保存周期不写死，按实际性能设计；原则是不影响输入体验同时最大程度避免丢失 |
| 存储 | Local First；首版不做云数据库、账号、Web 后端、多用户、服务端同步；SQLite 作为主要 Source of Truth；Markdown / JSON 仅作导出、备份、调试格式，不作为实时主数据库 |
| 检索 | 基础记录稳定后支持查看今天、查看指定日期、全文搜索、修改、删除、复制、按时间排序；首版搜索可基于 SQLite；不引入 Elasticsearch / Meilisearch 等独立搜索服务 |
| AI 总结 | 对每天全部 Entry 做总结；原始记录与 AI 结果必须分离，AI 不得修改或替代 Entry；Summary 为可重新生成的派生数据 |
| 总结内容 | 当日概览、项目、决定、TODO、想法、待解决问题、后续事项；同时输出给用户阅读的自然语言总结与程序可用的结构化结果 |
| 触发方式 | 支持手动生成；支持可配置的自动生成；自动执行不能依赖「每天 00:00 定时运行」，需能补偿关机/未启动/休眠导致的漏执行；任务应可重复执行、可恢复、幂等 |
| 过期机制 | 总结生成后若当天又新增或修改 Entry，原总结不再代表完整当天内容；用户应能看到「今日总结已过期」并重新生成 |
| AI Provider | 不与具体供应商强耦合；统一 Provider 抽象；至少覆盖 OpenAI-compatible API（可接入 OpenAI、其他兼容云模型、LM Studio、Ollama 等）；配置至少包含 Provider、Base URL、API Key、Model；首版优先设计好抽象，再实现一个可用 Provider |
| AI 调用原则 | AI 总结属后台批处理，不参与 Quick Capture 实时保存流程；保存 Entry 只写本地数据库，不等待 AI；AI 服务不可用不得影响正常记录 |
| 技术栈倾向 | 优先考虑 Tauri 2 + Vue 3 + TypeScript + SQLite + Rust，但要求重新验证而非照搬；不为了用 Rust 而把业务逻辑放进 Rust |

### 2.5 需求冲突与修正

以下是本轮识别出的需求内部张力，已给出处理结论，作为后续实现的前提。

| # | 冲突/模糊处 | 分析与结论 |
|---|---|---|
| 1 | 「窗口自动聚焦输入」×「尽量避免抢占用户原应用工作流程」 | 要接收键盘输入（尤其 CJK 输入法）就必须激活窗口并获得键盘焦点，二者不可兼得。macOS 的 non-activating panel 方案代价是无法正常输入中文，直接违背核心需求。**修正为：短暂抢占焦点，隐藏后归还焦点给原应用**，不追求"不抢焦点"。 |
| 2 | 「Esc 快速隐藏」×「不能丢内容」 | 若 Esc 等于隐藏并丢弃，会直接损失正在输入的内容。**定义：Esc = 保留草稿并隐藏**，不提供取消语义。 |
| 3 | 「自动总结可配置时间」×「不能依赖定时任务」 | 定时器在关机/休眠时不存在。**改为声明式期望状态 + 对账扫描**，不试图补执行"错过的定时点"（详见 §7.5）。 |
| 4 | 自动总结的目标日期未定义 | 当天仍在继续记录，当天总结生成后极易立刻过期，浪费 token。**用户决定：MVP 仅手动生成**，自动触发整体后移到阶段 4。 |
| 5 | 默认快捷键存在系统级冲突风险 | `Ctrl+Shift+Space` 在 Windows 上与中文输入法及部分 IDE 冲突概率高；`Cmd+Shift+Space` 在 macOS 上也可能被输入法或其他应用占用。**保留默认值，但注册失败必须可见并提供一键换键**；实际占用情况在阶段 1 真机核实。 |
| 6 | 「跨午夜后的正确日期归属」 | 若日期在读取时由时间戳动态推导，时区变更或夏令时会改变历史记录的日期归属。**日期在写入时固化为独立列**，并提供显式的"移动到其他日期"操作，不做自动重算。 |
| 7 | 「快速暂停或退出」中"暂停"语义未定义 | **约定：暂停 = 注销全局快捷键**（阶段 4 起追加"暂停自动总结"）；退出 = 完整退出应用。 |
| 8 | Markdown / JSON 的定位 | 若将来做双向同步会产生无法自动合并的冲突。**明确为单向派生输出，绝不回读**。 |
| 9 | 草稿数量未定义 | 「再次调起恢复未完成草稿」隐含单草稿。**MVP 采用全局单一 active draft**，表结构预留多草稿扩展位。 |
| 10 | 「便携版（不打包）」×「开机自启」×「可配置数据目录」 | 便携版要求数据与配置随目录整体搬移、免安装免管理员权限；而开机自启依赖系统级注册（Windows 注册表 Run 指向 exe 绝对路径，目录一移动即失效；macOS 需登录项授权），可配置数据目录则与「整个文件夹可搬移」的语义冲突。**结论：不做开机自启（由用户手动启动后长期常驻）；数据与配置固定在便携目录内，移除 MVP 中的「数据目录」设置项。** 代价：忘记启动则当天无记录——用户已确认接受。 |

## 3. 技术栈与选型

### 3.1 结论

| 层 | 选型 |
|---|---|
| 桌面运行时 | Tauri 2（Windows + macOS） |
| 前端 | Vue 3 + TypeScript + Vite |
| 样式/组件 | 按 `vue-ts-spec` 规范实施（实施前先读取规范与仓库事实） |
| 数据库 | SQLite，通过 `tauri-plugin-sql`（sqlx）访问，SQL 与数据语义留在 TypeScript |
| 数据库迁移 | 在 Rust 侧声明 migration |
| AI 请求传输 | 自定义 Rust 薄命令（reqwest），只做"发请求、回内容" |
| 系统能力 | Rust 壳：窗口生命周期、全局快捷键、托盘/菜单栏、单实例 |
| 分发形态 | 便携版：直接运行构建产物，不产出安装包，不做签名与公证 |
| 状态管理 | 仅在确有跨窗口共享状态时引入 Pinia |
| 数据访问层 | 不使用 ORM，使用参数化 SQL + 轻量封装 |
| AI SDK | 不引入 Vercel AI SDK；首版仅一个 OpenAI-compatible 直连实现 |

选型依据说明：

- **不使用 ORM**：本项目 SQL 简单，ORM 带来的映射层与迁移工具收益低于其维护成本。
- **不引入 AI SDK**：AI SDK 的价值集中在多 Provider 适配、流式输出与工具调用，本项目首版均不需要；直接 POST + Zod 校验即可，避免额外依赖。
- **AI 请求不走 `tauri-plugin-http`**：该插件通过编译期 capabilities 中的 URL glob 做静态 scope，而 Provider 的 Base URL 需要用户运行时配置（OpenAI / 兼容云服务 / LM Studio / Ollama / 私有网关），静态白名单会直接冲突。改用只做传输的自定义 Rust 命令。**该插件的 scope 机制依据官方文档；是否支持运行时扩展 scope 未核实**，阶段 3 前确认，若不支持则按本方案执行。

### 3.2 与 Electron 的对比结论

Electron 曾作为主要备选，最终未采用。对比如下（权重列体现本项目实际优先级）：

| 维度 | Tauri 2 | Electron 44 | 本项目权重 |
|---|---|---|---|
| 语言/工具链 | 需 Rust 工具链 + MSVC Build Tools，双语言 | 全 TS，唯一工具链 Node | 中 |
| 全局快捷键 | 官方插件，Carbon `RegisterEventHotKey`，不需辅助功能权限 | 内置 `globalShortcut` | 中 |
| 托盘/菜单栏 | 官方插件 | 内置 | 中 |
| 窗口显示/聚焦 | 存在公开未决问题（见 §6.2） | 成熟多年 | 高 |
| 中文 IME | 依赖 WebView2 / WKWebView，存在公开问题（见 §6.2） | 捆绑 Chromium，行为跨平台一致 | 高 |
| 数据库 | `tauri-plugin-sql` | `better-sqlite3`（同步 API） | 中 |
| 密钥保护 | 无内置等价物 | 内置 `safeStorage`（DPAPI / Keychain） | 低 |
| 体积/内存 | 更小 | 更大 | 低（自用单机） |
| 业务逻辑位置 | 需明确划分 Rust / TS 边界 | 天然全 TS | 中 |

**结论**：本项目把可靠性押在「快捷键 → 窗口 → 中文输入 → 落盘」这条路径上，该路径在 Electron 侧更成熟、平台差异更少；Tauri 的优势（体积、内存）对自用单机工具收益有限，而代价是第二套工具链与 WebView 差异外溢到业务层的风险。

**用户最终选择 Tauri 2**，主要考量是资源占用与统一技术栈方向。因此 §4 的 Rust / TS 边界设计与 §6.2 的风险规避是本方案的核心内容，用于把 Tauri 侧的已知不确定性限制在可控范围内。

## 4. 系统架构

### 4.1 分层与进程边界

```
┌─ WebView（Vue 3 + TypeScript）—— 全部业务规则与数据语义
│   capture 窗口：草稿读写、提交事务、幂等去重、显示后同步
│   main 窗口：Entry 增删改查、日期视图、搜索、总结展示、设置
│   业务域模块：entry / draft / summary / settings（SQL 就近写在域模块内）
└──┬── tauri-plugin-sql → SQLite（Source of Truth，位于便携目录 data 子目录）
   ├── 自定义 Rust 薄命令 `ai_request` → reqwest 发起 AI 请求（无 CORS 限制）
   └── Tauri IPC 与 capabilities（最小权限白名单）
┌─ Rust 壳（src-tauri）—— 不做业务判断
│   ShellCore      窗口创建、show / hide、聚焦、定位、macOS activation policy
│   Hotkey         全局快捷键注册与失败反馈
│   Tray           托盘 / 菜单栏、暂停、退出
│   SingleInstance 单实例
│   DbInit         数据库路径、连接、migration 声明、WAL 与 busy_timeout
│   （阶段 4 预留）Ticker：只负责"何时提醒"，不判断"做什么"
└─ 存储：SQLite。派生输出：JSON / Markdown 导出（单向）
```

### 4.2 Rust / TS 边界原则

**「何时」与「系统」归 Rust，「做什么」与「规则」归 TS。**

| 归 Rust | 归 TypeScript |
|---|---|
| 窗口创建、显示/隐藏、聚焦、屏幕定位 | 全部数据语义与业务规则 |
| 全局快捷键注册与冲突反馈 | 草稿保存策略、提交事务、幂等去重 |
| 托盘/菜单栏、单实例 | Entry 增删改查、搜索、日期视图 |
| macOS activation policy 等平台分支 | 总结编排、提示词组装、结构化校验、过期判定 |
| 数据库连接、migration 声明、连接级 PRAGMA | 参数化 SQL 与任务状态机 |
| AI 请求的网络传输（不含任何提示词或解析逻辑） | AI 任务幂等、重试判断、失败原因归类 |
| 阶段 4：定时与唤醒等触发时机 | 阶段 4：对账逻辑（判断"该做什么"） |

约束：

- TS 侧唯一的平台分支是快捷键默认值（`Ctrl` vs `Cmd`），其余业务代码不出现平台判断。
- Rust 壳不包含任何业务判断；AI 传输命令不感知提示词、模型与响应结构。
- 不建立 Repository / Manager / Handler 抽象层，不建接口与工厂，不做依赖注入容器。每个业务域一个模块，SQL 就近书写。

### 4.3 主要交互路径

```
快捷键（Rust 注册）→ Rust 显示并聚焦 capture 窗口
                  → TS 通过 DOM focus / visibilitychange 感知
                  → 幂等 syncFromDb()：读取 draft → 载入 textarea → 聚焦
输入              → 输入停顿触发草稿 upsert（参数化 SQL）
Ctrl/Cmd+Enter    → 单事务[插入 entry + 清空 draft] → 隐藏窗口
Esc               → 保留草稿 + 隐藏窗口 + 归还焦点
```

硬约束：**该路径中不存在任何 AI、网络请求或批量计算。** AI 只出现在 SummaryService 的独立任务里，与捕获路径物理隔离。

### 4.4 前端窗口组织

- capture 窗口与 main 窗口使用各自独立的 HTML 入口：capture 入口保持极小体积以保证快速显示，main 窗口允许按需懒加载。
- capture 窗口在应用启动时即创建并加载页面（隐藏状态），使首次调起也是热态。
- 隐藏窗口的 WebView 定时器可能被节流，因此**任何定时逻辑不得依赖隐藏中的 capture 渲染进程**；阶段 4 的调度触发点放在 Rust，业务判断放在 TS。

## 5. 数据模型

### 5.1 表结构概览

| 表 | 职责 | 关键点 |
|---|---|---|
| `entry` | 一条用户主动记录 | `id`（UUID，由 TS 生成）、`content`、`created_at`（UTC 毫秒）、`updated_at`、`local_date`（写入时固化）、`deleted_at`（软删除） |
| `draft` | 未提交的快速记录输入 | MVP 仅一行（固定 id），`content`、`updated_at`，预留 `session_seq` |
| `daily_summary` | 某日 AI 总结（派生数据，可整体删除重建） | `local_date` 唯一、`payload`（JSON）、`source_revision`、`provider`、`model`、`prompt_version`、`generated_at` |
| `ai_job` | AI 任务的执行状态与幂等依据 | `(type, target_date)` 唯一、`status`、`attempts`、`last_error`、`source_revision` |
| `settings` | 用户配置（KV，值为 JSON） | 快捷键、Provider 配置（不含 key）、暂停状态 |
| 迁移版本（SQLx 内部账本） | Schema 版本 | Rust 声明 migration，复用 SQLx 迁移机制及内部 `_sqlx_migrations` 账本；不使用 `PRAGMA user_version` 自制迁移 |

### 5.2 关键设计决策

**日期写入时固化。** `created_at` 为 UTC 时间戳，`local_date` 在写入时按当前时区固化为独立列，按 `local_date` 建立索引。理由：避免时区变更或夏令时导致历史记录的日期归属漂移。修改 Entry 内容不改变 `local_date`；跨日期移动作为显式操作提供（非 MVP）。

**原始记录与 AI 结果物理隔离。** SummaryService 只持有 `entry` 的只读查询；代码结构中不存在任何由 AI 路径发起的 `entry` 更新语句。AI 失败或输出不合法只影响 `daily_summary` 与 `ai_job`。这是「AI 不得修改或替代原始记录」这一需求的结构性保证，而非依赖代码审查。

**过期判定使用内容指纹，而非"最新更新时间"。** 

```
source_revision = hash(按 id 排序的 [entry_id, updated_at, content_hash] 集合)
```

选择理由：单一时戳在编辑不改动"最新时间"先后关系、系统时钟回拨、时间戳精度不足时会漏判；一天记录数量有限，指纹计算成本可忽略。收益是过期判定完全无状态——读取时比较两个字符串即可，不需要在写入 Entry 时维护"过期标志"，也就不存在标志与实际不一致的失败模式。

**删除采用软删除。** 成本仅为一个查询过滤条件，收益是误删可恢复，且不会因一次误删让历史总结与任务状态的语义混乱。彻底清理已删除记录作为显式操作提供（非 MVP，且须单独授权）。

**结构化提取结果存 JSON 列，不拆分为多张表。** 六类字段（projects / decisions / todos / ideas / open_questions / follow_ups）同一次生成、同一生命周期、首版仅只读展示，拆表只增加 join 与写入复杂度。将来若需独立管理 TODO，再做迁移（开发期不要求兼容旧数据）。

**`ai_job` 在仅手动模式下仍然保留。** 用途：防止重复点击"生成总结"导致重复消耗 token、记录失败原因、保证重试幂等。自动触发所需的调度字段（如 `next_run_at`）留到阶段 4 再增加。

**API Key 存储策略。** Tauri 无 Electron `safeStorage` 的等价内置能力。便携版的要求是数据与配置随目录整体搬移，而操作系统凭据库（Windows Credential Manager / macOS Keychain）绑定的是机器而不是目录，`keyring` crate 方案与便携语义直接冲突，因此由「首选方案」降为备选。阶段 3 在以下两种方案间定案：一是便携目录内加密文件 + 由用户口令派生的加密密钥；二是明文存储 + 明确风险提示（本地单机、文件权限受便携目录保护）。Provider 的非敏感配置在两种方案下均存 `settings`。

### 5.3 数据流与生命周期

| 数据 | 产生 | 变更 | 失效 |
|---|---|---|---|
| `entry` | 用户提交 | 用户编辑（更新 `updated_at` 与内容指纹） | 用户删除（软删除） |
| `draft` | 用户输入 | 输入停顿覆盖写 | 提交成功后清空 |
| `daily_summary` | AI 生成成功 | 重新生成时覆盖 | 当日 `source_revision` 变化即视为过期 |
| `ai_job` | 生成请求 | 状态机推进 | 完成后保留作为幂等依据 |

### 5.4 索引方向

按 `local_date` 建立 `entry` 查询索引（含软删除过滤）；`daily_summary.local_date` 唯一；`ai_job (type, target_date)` 唯一。具体索引语句在阶段 2 结合实际查询确定，此处不写 DDL。

### 5.5 迁移、事务与崩溃恢复

- 迁移：基于 Schema 版本的顺序迁移脚本，由 Rust 侧声明；开发期允许删库重建。
- 事务：提交 Entry 与清空草稿必须在同一事务内，避免"记录已保存但草稿未清"或反之。
- 连接级设置：WAL 日志模式与 `busy_timeout`，在 `DbInit` 建立连接时设置。
- 数据库路径：位于便携目录的 data 子目录，Windows 与 macOS 共用同一套解析逻辑；开发态显式指向项目内目录，避免数据落在 `target/` 下被 `cargo clean` 连带删除；启动时检测目录可写性，不可写则明确报错，不静默降级。
- 持久性取舍：WAL + `synchronous=NORMAL` 保证进程崩溃不丢已提交事务，但操作系统崩溃或断电可能回滚最近的已提交事务。草稿路径对丢失最敏感，是否对草稿写入使用更强的同步等级，在阶段 1 结合实测写入频率决定。
- 备份：使用 SQLite 的一致性备份能力导出，而不是直接复制数据库文件。具体方式在阶段 2 确定。

### 5.6 搜索

MVP 采用参数化子串匹配（`LIKE`），不引入 FTS5。理由：一方面 SQLite 官方 amalgamation **默认关闭 FTS5**，需显式编译选项，可用性依赖所选 Rust SQLite 依赖的编译配置；另一方面 FTS5 的默认分词器对中文无效（中文无词边界，连续汉字会被视为单个 token），要中文可用需 `trigram` tokenizer。在个人记录规模下子串匹配足够且零风险。**FTS5 与 trigram tokenizer 的可用性在阶段 2 结合真实数据量与所选依赖一起核实**，不作为已定实现。

## 6. Quick Capture 设计

Quick Capture 是本项目最重要的功能，其可靠性优先级高于一切其他设计。

### 6.1 窗口生命周期：预创建，只显示/隐藏，不销毁

- 应用启动时一次性创建 capture 窗口：无边框、置顶、不显示在任务栏、不可缩放、初始隐藏，并立即加载页面。
- 快捷键触发后 `show()` → 聚焦；隐藏用 `hide()`，**不销毁、不重建**。
- 位置：优先使用上次记录的位置；无记录时出现在**鼠标所在显示器**的偏上居中位置（多显示器场景必须处理）。
- 显示前先完成内容同步，避免出现"先显示空窗口再填充"的闪烁。

### 6.2 焦点策略与已知问题规避

Tauri 侧存在与本项目关键路径直接重叠的公开问题，方案需做结构性规避，而不是依赖"但愿不复现"：

| 已知问题 | 与本项目的关系 | 规避设计 |
|---|---|---|
| 隐藏创建的窗口可能永久收不到事件，`EvaluateScript` 被静默丢弃（2026-07 报告） | 命中"隐藏的 capture 窗口需要在显示时收到通知" | **关键路径不依赖 Tauri 事件通道**：快捷键注册与窗口显示均在 Rust 完成；TS 通过 WebView 自身的 DOM `focus` / `visibilitychange` 感知窗口出现并触发幂等同步 |
| `show()` 后立即 `set_focus()` 可能失效；需 hide → unminimize → set_focus 才生效 | 命中"快捷键后立刻可输入" | Rust 侧采用 `unminimize()` → `show()` → `set_focus()` 顺序并在必要时追加一次聚焦；TS 侧再补 `<textarea>.focus()`，形成两级双保险 |
| Windows WebView2 中，`<textarea>` / contenteditable **已有文本**时首次聚焦可能冻结 TSF，CJK 输入法无法输入 | 命中"恢复草稿后继续输入中文"，这是本产品的第一功能 | 仅使用普通 `<textarea>`，不使用 contenteditable 富文本编辑器；阶段 1 在真机实测"已有草稿 + 中文输入"场景 |

**多触发源 + 幂等同步**：DOM `focus`、`visibilitychange`、Tauri 事件、用户首次输入均触发同一个幂等函数 `syncFromDb()`；任一通道可用即可正常工作，重复触发无副作用。

**降级方案**：若阶段 1 实测显示隐藏窗口的通知仍不可靠，则改为每次调起时销毁并重建 capture 窗口。代价是首次可输入时间退化到数百毫秒级，不影响数据正确性。

### 6.3 草稿与自动保存

| 场景 | 行为 |
|---|---|
| 输入过程 | 按**输入停顿**触发草稿覆盖写（非固定高频周期） |
| 窗口隐藏 / 失焦 | 立即 flush 一次（兜底，防止"刚打完就 Esc"） |
| 应用退出前 | flush |
| 进程/系统崩溃 | 丢失量 = 最后一次 flush 之后的输入；这是"不写死周期"设计下必须接受的残差 |
| 再次调起 | 恢复内容与光标位置；确保"输入框已有内容时中文输入法首次聚焦即可用" |
| 提交成功 | 单事务写 `entry` + 清空 `draft`，随后隐藏窗口 |

草稿保存周期的具体数值（输入停顿时长、最大等待上限）在阶段 1 使用实测数据在"写入次数 / 输入延迟 / 崩溃丢失窗口"三者间校准，本文不预设常数。

### 6.4 交互细节

- `Esc` = 保留草稿 + 隐藏（需阻止默认行为，避免触发窗口关闭或退出）。
- `Ctrl/Cmd + Enter` = 提交并隐藏；`Enter` = 换行（多行输入优先）。
- 快捷键再次按下 = 切换显示/隐藏，应对误触。
- 提交幂等：`entry.id` 由 TS 预生成 UUID，重复提交（手抖连按）不会产生两条记录。
- 空内容提交 = 直接隐藏，不写 `entry`。
- 暂停状态：仅注销全局快捷键，不做其他降级。

### 6.5 快捷键与冲突处理

- 默认值：Windows `Ctrl + Shift + Space`；macOS `Cmd + Shift + Space`。支持用户自定义。
- 注册失败（快捷键已被占用）时：托盘提示 + 设置页高亮 + 提供候选键，**绝不静默失败**——否则用户会误判为程序故障。
- 能力边界：系统热键接口只能判断"注册是否成功"，无法获知被哪个程序占用。UI 文案须与之相符，不做无法兑现的承诺。
- 已知高风险键位：Windows 中文输入法切换、macOS 输入法与 Spotlight/应用快捷键。实际占用情况在阶段 1 在真机核实。

### 6.6 后台常驻与平台差异封装

| 能力 | Windows | macOS | 业务层可见性 |
|---|---|---|---|
| 常驻入口 | 托盘图标 + 右键菜单 | 菜单栏图标（隐藏 Dock 图标） | 无 |
| 关闭主窗口 | 隐藏而非退出 | 隐藏而非退出 | 无 |
| 数据与配置目录 | 便携目录 data 子目录 | 同 | 无 |
| 睡眠恢复 | 监听 resume → 重新校时 + 触发一次检查 | 同 | 无 |
| 单实例 | 单实例插件 | 同 | 无 |

平台分支全部收敛在 Rust 壳内，业务代码只调用统一抽象。

### 6.7 响应时间目标

以下为产品层面的期望值（用户明确要求可测指标），**当前为待实测校准的目标值，不是已测数据**：

| 场景 | 目标（热态：应用已常驻） |
|---|---|
| 按下快捷键 → 窗口首帧可见 | p50 ≤ 100ms，p95 ≤ 200ms |
| 按下快捷键 → 输入框可输入（含中文输入法可用） | p50 ≤ 150ms，p95 ≤ 300ms |

| 空闲驻留 CPU | 采样期内无持续占用 |
| 空闲磁盘写入 | 仅在事件发生时写，无周期性写入 |
| 冷启动（手动启动到快捷键可用） | 记录实测基线作为回归参照，不设硬上限 |

具体测量方法与判定方式留到阶段 1 单独讨论。

## 7. AI 总结方案

### 7.1 结构化输出 Schema

在需求给出的字段基础上做一处增强：每个条目从裸字符串改为带来源引用对象。

```json
{
  "summary": "一段自然语言总结",
  "projects":       [{ "text": "...", "entry_ids": ["..."] }],
  "decisions":      [{ "text": "...", "entry_ids": ["..."] }],
  "todos":          [{ "text": "...", "entry_ids": ["..."] }],
  "ideas":          [{ "text": "...", "entry_ids": ["..."] }],
  "open_questions": [{ "text": "...", "entry_ids": ["..."] }],
  "follow_ups":     [{ "text": "...", "entry_ids": ["..."] }]
}
```

增强理由：让结构化结果可回溯到原始记录（UI 可跳转），这是"AI 结果与原始记录分离"要求的自然延伸；同时 `entry_ids` 也是校验 AI 是否编造内容的依据。Schema 校验失败则整次生成判为失败，不写入半成品。

### 7.2 Provider 抽象

- 唯一实现：OpenAI-compatible `chat/completions`（`baseUrl` + `apiKey` + `model`）。该接口同时覆盖 OpenAI、兼容云服务、LM Studio、Ollama，首版一个实现即可满足全部目标。
- 结构化输出策略：优先请求 `response_format: json_schema`（约束解码）；模型不支持时降级为 `json_object` + Schema 校验 + 重试。**能力探测结果按模型缓存**，避免每次试错。
- 抽象边界：TS 侧定义"生成某日总结"的单一入口，内部完成提示词组装、请求、校验、解析；Rust 侧只提供传输命令。
- 失败分类：网络错误、超时、限流、鉴权失败、模型不存在、输出非法分别归类；可重试类进入退避重试，不可重试类直接置失败并在 UI 给出可读原因。

### 7.3 手动生成流程

```
用户点击"生成今日总结"
→ 查 ai_job：(type, target_date) 状态为 running → 忽略本次点击
→ 已有成功总结且 source_revision 与当前一致 → 直接返回现有结果
→ 否则创建/更新 job 为 running
→ TS 组装提示词 → Rust 传输命令发起请求 → TS 校验解析
→ 单事务写 daily_summary + 置 job 成功
```

### 7.4 过期判定与展示

```
current_revision = hash(当日有效 entry 的 (id, updated_at, content_hash) 排序集合)

daily_summary.source_revision == current_revision → 有效
否则                                            → 已过期（显示"今日总结已过期 + 重新生成"）
无 daily_summary                                → 未生成
```

由于修订号在读取时计算，不存在"标记未及时更新"的失败模式。默认**不自动重新生成**（避免反复消耗 token），由用户决定。

### 7.5 自动触发与补偿（阶段 4，位置已定）

统一模型：**「某日应当存在一份与当前记录内容一致的总结」是期望状态；`ai_job` 是执行记录；对账扫描负责使两者一致。**

| 触发源 | 行为 |
|---|---|
| 手动 | 入队并立即执行（阶段 3 实现） |
| 应用启动 | 必然执行一次对账扫描（**这是"不遗漏"的保证来源**） |
| 系统唤醒 | 执行一次对账扫描并重新校时 |
| 日期跨越 | 执行一次对账扫描 |
| 低频定时 | 仅作为加速手段，不作为正确性保证 |

幂等保证：`(type, target_date)` 唯一约束使同日不会产生两个任务；任务携带 `source_revision`，执行前比对，一致且已有成功结果则直接跳过；应用异常退出时处于执行中状态的任务在下次启动被识别为中断并重新入队；同一修订号重复执行不产生副作用。

**为什么不用"补跑错过的定时任务"**：补跑需要维护"哪些定时点被错过"的账本，而关机、休眠、时区变化都会污染该账本。对账扫描不需要账本，任何时刻启动都能得出正确结论——这也直接回应用户提出的"电脑可能关机、软件可能未启动、系统可能休眠"问题。

自动运行的触发时机由 Rust 提供，业务判断由 TS 完成，以规避隐藏 WebView 定时器被节流带来的不确定性。

### 7.6 边界

AI 服务不可用、未配置或返回异常，均不影响记录功能（两者之间没有数据依赖）。AI 只能读取 `entry`，只能写入 `daily_summary` 与 `ai_job`。首版不做 RAG、Embedding、向量库、Agent、逐条分类与实时对话。
